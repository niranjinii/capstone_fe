## Category 1: Core Privacy Features (The Big Three)

### 1. Result Privacy via rho Blinding (Design A) — NOT STARTED
**Roadmap: Section 5.4b, Section 0.5 (Design A)**

The Cloud currently sees the raw risk score (`190984`). It should see random noise.

**What needs to happen:**
- `hospital.py`: Generate random rho, extend the weight vector to [y, rho] (dimension n+1), generate FeDDH keys for the extended vector. Seal rho and send it to the Clinic separately.
- `clinic.py`: Extend the patient vector to [x, 1] (so the dot product becomes <x, y> + rho). Receive rho from Hospital via a sealed channel. After getting the Cloud's response, subtract rho locally.
- `cloud.py`: No changes to the evaluation logic — it just computes the blinded result.

**CRITICAL: Decryption Algorithm Upgrade Required.** The Cloud's current `FeDDH.decrypt()` uses a linear brute-force scan over `(-1000000, 1000000)`. With rho blinding, the effective search range expands to R = S + |rho|. If rho is large, linear search is infeasible. You **must** implement a Baby-step Giant-step (BSGS) or Pollard's Kangaroo discrete-log algorithm. PyMIFE does not provide one.

**NOTE: Timing Side-Channel.** Even with rho blinding, the Cloud's decryption time correlates with the magnitude of the blinded score. A constant-time search or BSGS (more uniform timing) should be considered.

**Estimated effort:** 2-3 days (including BSGS implementation)

### 2. Query Privacy via Intermediate Buckets — NOT STARTED
**Roadmap: Section 5.4a, Section 3 (Choice 3)**

The Cloud can identify the cancer model from the vector dimension alone (139 = ACC, 252 = BRCA, 28 = GBM, etc.).

**IMPORTANT: The FHIPE Wall.** `check1_gene_union.py` shows that the global gene union (n ~ 3,555) falls in the `> 1500` branch, which is explicitly labelled "UNAVAILABLE UNDER FHIPE" due to O(n^3) setup cost and O(n^2) encryption cost. Padding all vectors to the union dimension is **not a viable option** under FeDDH.

**The only feasible approach: Intermediate Buckets**
- Group the 33 cancers into ~10 clinical families (e.g., Gastrointestinal, Gynecological, Hematological) and pad to a per-family bucket dimension (n ~ 300-500)
- `hospital.py`: Pad weight vector with zeros to the bucket dimension. Generate keys at the bucket dimension, not the model dimension.
- `clinic.py`: Pad patient vector with zeros to match. Encrypt at the bucket dimension.
- Need to define the actual clinical bucket groupings (which cancers go together)
- Run `check1_gene_union.py` on real weights first to confirm the exact union size and per-cancer counts before deciding bucket boundaries.

**Estimated effort:** 2-3 days (including deciding the bucket groupings)

### 18. Delegated Encryption Key (ek) Rotation — NOT STARTED *(NEW)*
**Source: `publish_recommendations.md` Section 3b**

The delegated encryption key ek is sent once and reused for every query. If the Clinic is compromised after receiving ek, the attacker gains permanent encryption capability.

**What needs to happen:**
- Define a key lifetime policy (e.g., ek expires after T queries or a time window)
- Implement ek rotation: Hospital re-runs Setup with fresh B, regenerates ek, and pushes it to the Clinic
- Optionally: encrypt ek at rest on the Clinic's device
- At minimum: discuss this in the paper's threat model section, even if not fully implemented

**Estimated effort:** 1 day (implementation) or 1 hour (paper discussion only)

### 19. Ciphertext Replay Attack Prevention — NOT STARTED *(NEW)*
**Source: `publish_recommendations.md` Section 3c**

Nothing currently prevents the Cloud from replaying an old ciphertext against a new functional key, or vice versa.

**What needs to happen:**
- Add a query_id or nonce + timestamp to the JSON payload metadata
- Bind the ciphertext to a specific functional key via a commitment scheme
- The Cloud should reject payloads with duplicate or expired query IDs

**Estimated effort:** Half a day (basic nonce/timestamp), 2 days (full commitment scheme)

### 20. Weight Quantisation Sign Bug — DONE
**Discovered during audit. Fixed 2026-08-25.**

`hospital.py` previously applied `abs(val) + 1` during quantisation, which destroyed the sign of negative Lasso coefficients.

**Fix applied:** Replaced with a constant-shift approach. All weights are shifted by `C = |min(quantized)| + 1` to ensure strict positivity (avoiding PyMIFE's k2=None bug on zero weights). The Clinic subtracts `C * sum(x)` from the Cloud's result to recover the true dot product.

**Verified:** `verify_sign_fix.py` confirmed 0.00% error across all 33 cancer models (old method had 62%–6,143% error).

**No further action needed.**
